## 1. Executive summary

Fabric ("Anchor AI") is **100% deterministic, client-side, on-device logic**. There is **no external LLM/model/provider call anywhere in the audited path** — no OpenAI/Anthropic/Gemini/Vertex/Bedrock/HuggingFace/custom inference client exists in `src/`, `functions/src/`, `packages/`, `config/`, or environment configuration (§3). "AI" is branding over hand-written heuristics, regex intent parsing, and frequency counters. Prompt-injection and model-output-validation threat models are **NOT APPLICABLE** (§21/§22).

Fabric knows: transactions (title, amount, category, currency, scope), commitments (title, completion, streak, timeOfDay, daysOfWeek), accounts (balances), recurring rules, the profile timezone, ambient clock data, mood entries, and its own persisted learning state (patterns/predictions/conversations/reports/settings). All of it is read from the user's own `artifacts/anchor-os/users/{uid}/**` tree and written back under the same tree. Nothing leaves Firebase/AnchorOS except FCM push bodies generated by three scheduled Cloud Functions and one scheduled weekly report (§13).

Verdicts at a glance:

## 6. Context construction

Initial load (`initializeFabricState`, `loadFabricActivity`): `finance` (**no constraints → full history, no limit**), `commitments` (**unbounded**), `accounts` (unbounded), recurring rules (`where userId==uid`; errors swallowed → `[]`). Live replacement (`useFabricLiveSync`): finance **newest 500 within last 1 year** (ISO-string `date >=` comparison, `orderBy desc, limit(500)`), commitments unbounded, accounts `limit(50)`, recurring unbounded.

- **Window inconsistency (FB-11):** after the first live finance snapshot, a >500-transaction user's context silently shrinks from "all history" to "500 newest"; >1-year-old data always drops out of live mode. Insights/predictions computed before vs after the first snapshot can differ with no user-visible change.
- Filters: most engines filter `type==='expense' && !isSoftDeleted`; WeeklyReportEngine's current-week totals **omit the soft-delete filter** while `vsLastWeek` applies it — internally inconsistent.
- Deduplication: none needed (full snapshot replacement per listener).
- Optimistic state: Fabric reads Firestore snapshots, but commitments use `memoryLocalCache`, so optimistic/unconfirmed mutations surface to Fabric through the same listener.
- Family/shared data: Fabric reads only the user's own collections. Family-scoped rows (`scope:'family'`) replicated into the user's `finance` collection (ref FS-05) are blended into personal aggregates; `buildFamilyInsight`/`familySummary` isolate them by `scope` for display only.
- Currency: `detectPrimaryCurrency` takes the **first** transaction's currency; aggregation is currency-blind (mirrors FI-12).
- Timezone: ambient context uses profile `timezone`, else **UTC fallback** (FB-16); day-of-week engines use device-local time — three clock domains coexist.
- Deleted/archived data: archived accounts filtered in queries; deleted commitments vanish from inputs but their learned patterns persist (FB-03).

**Answer:** YES — stale (optimistic/local-cache), duplicated (offline-queue double-import, FI-06), family-scoped, and currency-mixed data can contaminate Fabric's user model; scope isolation itself is sound (own-tree only).

## 7. `useFabricLiveSync` (first-class ingestion boundary)

`src/context/fabric/useFabricLiveSync.ts:14-79` — four independent `onSnapshot` listeners, each replacing a ref array wholesale and calling `push()` → `updateActivity(...)` + `refresh()`.

| Property | Finding |
|---|---|
| Subscriptions | finance (where+orderBy+limit 500), commitments (raw collection), accounts (limit 50), recurring (`where userId==uid`) |
| Owner filtering | finance/commitments/accounts are path-bound subcollections of the authenticated user's doc; recurring filtered `userId==uid`. `recurring_transactions` rules also grant read on `sharedWith` rows, but the Fabric query is owner-only — no over-collection |
| Update frequency | one refresh per snapshot change per listener; no debounce/throttle (recomputes are lazy, gated by `predictionsDirty` — bounded) |
| Ordering | finance newest-first; no cross-listener ordering guarantee (harmless — wholesale replacement) |
| Initial snapshot | each listener fires with full current data on attach |
| Reconnect | Firestore SDK auto-reconnect + fresh snapshot → self-healing; replacement semantics mean no merge drift |
| Logout/user-switch teardown | effect deps `[userId, isEnabled, refresh, fabricService]`; cleanup unsubscribes all four. **But see FB-01**: teardown is listener-level; the singleton service's in-memory state is NOT reset (`dispose()` only cancels the save timer) |
| Duplicate listeners | none — single effect instance |
| Stale closures | data held in refs; `push` closes over stable callbacks |
| Deleted docs | removed by snapshot replacement |
| Error handling | **no `error` callbacks on any listener** — a stream/permission error silently leaves the last snapshot in place |

### User switch (A logout → B login, same session)
Listeners tear down with A's userId and re-subscribe to B's path — listener-level isolation holds. **However** `FabricService` is a process-wide singleton: A's engine state (patterns/confidence/recentActions) remains in memory after A's teardown. `initialize(B)` sets `this.activeUserId = B` **synchronously**, then awaits several Firestore reads while the engine still holds A's state. Any `learnFrom` (e.g., a finance add or commitment toggle fired during B's login) in that window schedules a debounced `saveBehavior(B)` that **writes A's learned patterns into B's `fabric_behavior`**. Proven code path (FB-01); no test covers service-level user switch (only listener unmount is tested).

### Family state change
Fabric holds no family-derived state of its own: it ingests rows already replicated into the user's own collections. On disconnect, future ingestion of the ex-partner's data stops only insofar as the upstream writes stop — FS-01's rules-level read exposure is upstream of Fabric and is **not** widened by Fabric (Fabric never reads `family_connections` or shared docs directly).

### Rapid finance/task state changes
Wholesale snapshot replacement means a newer snapshot always fully replaces an older one; no merge path exists for a stale snapshot to overwrite newer data. The stale-overwrite risk in C-03 belongs to the commitments UI's 5 s polling, not to this listener.

### Offline/reconnect — double learning
Live-sync itself cannot double-learn (replacement semantics). Double-learning happens at the `learnFrom` layer (FB-02): each offline-queue flush attempt (and duplicate import per FI-06) produces another `learnFrom` call.

## 9. Pattern engine

Schema (`types/fabric.ts:25-51`): `UserPattern{id, trigger, followUpAction, frequency, confidence, lastOccurred, averageDelayMs, dismissed, createdAt, updatedAt}`; triggers: `commitment_completed|time_of_day|transaction_recorded|app_opened|page_visited|period_start`; actions: `record_transaction|check_commitment|view_page|review_budget|check_account`.

- Signature = full JSON of trigger+action (`behaviorEngineUtils.toSignature`) — two events differing in any field (e.g., different `commitmentId`) form distinct patterns. No normalization/collision handling; `app_opened` and `period_start` triggers are defined but **no caller emits them**.
- Confidence = `frequency/(frequency+dismissed+2)` × `(0.7 + 0.3 × recentOccurrences/frequency)`, clamped [0,1] (`behaviorEngineUtils.calculateConfidence`). Confirmed threshold 0.5; prediction-pattern gate 0.65.
- Frequency only ever increments (`recordAction`); nothing decrements it. Dismissal increments `dismissed` (softens confidence) but the pattern stays in `patterns` and future occurrences re-raise confidence — dismissal can be out-voted.
- Recent-actions buffer: max 100, 90-day TTL, 30-day recency window; persisted with `fabric_behavior`.
- Seeding: on first init with an empty store, `seedFromHistory` fabricates patterns from history (category with ≥2 expenses → `transaction_recorded→review_budget` at confidence ≥0.55; ≥2 completed tasks sharing `timeOfDay` → `time_of_day→check_commitment` at fixed hours 8/14/18). Seeds hardcode `lastOccurred = now` and `recentOccurrences = count` — confidence is inflated by construction.
- Persistence: single `fabric_behavior/state` doc; 500 ms debounce; last-write-wins whole-document replacement. No migration/versioning, no schema validation on load — a corrupted doc's fields are spread in as-is and malformed `patterns` arrays flow into every engine.
- Deletion: `deletePattern` removes from all three lists; `dismissedPatterns` prevents nothing (never consulted by `recordAction`).

Correctness under stress:

- duplicated/stale events → permanently inflate `frequency` (FB-02/FB-03);
- reversed (deleted) transactions → no compensation event exists (FB-03);
- deleted/uncompleted commitments → `commitment_completed` patterns keyed by dead `commitmentId` persist and still fire generic variants;
- missed recurrence → the `missed_habit` proactive question fires from `lastOccurred`, which seeds set to seeding time (wrong);
- family data → family-scoped expense rows feed `transaction_recorded` seeds like personal data;
- timezone change → `time_of_day` seeds use fixed hours mapped from labels, not observed times — a timezone change silently mislabels the trigger hour;
- behavior change → decay is only via the recency multiplier (min 0.7×) — **old bad events keep ≥70% of their confidence weight indefinitely**.

**Answer:** YES — a small number of bad/stale events permanently biases learned pattern state: frequency is monotonic, seeds inflate confidence, dismissal is advisory, and no expiry/decay removes patterns. Only manual `deletePattern` (or full clear) removes bias.

## 11. Briefing

`DailyBriefingEngine.buildDailyBriefing` (client, recomputed on every `refresh()` — not persisted, not cached):

- Inputs: current in-memory transactions/commitments/recurring; `timeOfDay` from ambient context (profile timezone, else **UTC fallback** — greeting can be wrong for users without a profile timezone, FB-16).
- Task filtering: `getTodayTasks` — daily always; todo always (all outstanding); **weekly matches single letters `['S','M','T','W','T','F','S']` against `daysOfWeek`** while forms write full day names (`'Sunday'…'Saturday'`, `TaskFormParts.tsx:68`, `EditTaskFormFields.tsx`) → **weekly commitments are invisible to the briefing AND the app badge** (`useCommitmentBadge` consumes the same function). Confirms C-06's Fabric/badge impact in current code (FB-04). Monthly tasks: `daysOfMonth`/`dayOfMonth` handled.
- Completed/missed: `task.completed` after the client-lazy daily reset (C-04) — a stale/un-reset task can show still-complete or still-pending against reality; "All tasks done today" can contradict the commitments screen.
- Finance: `spendingThisWeek` respects soft-deletes; upcoming bills from active recurring `nextRunAt` within 7 days (device-local midnight math); day-of-week signals use last 30 days device-locally.
- Multi-currency: primary-currency detection only; upcoming items carry `currency: undefined`.
- Failure behavior: pure function over possibly-empty arrays — degrades into misleading empty claims ("No scheduled tasks today…") when context failed to load.
- Stale transactions/pending bank sync: Mono rows are ordinary docs; an incomplete sync reads as genuine silence.

**Verdict:** briefing claims CAN contradict authoritative state — via C-06 (weekly invisibility), C-04 (client-clock reset), UTC fallback (FB-16).

## 12. Weekly report

Two independent implementations share one collection:

**Client (`WeeklyReportEngine`, on-demand button):** period = rolling `[now−6d, now]` device-local; current-week totals **omit the soft-delete filter** (vs `vsLastWeek` which applies it); commitments scoped by **createdAt in window** (a task created months ago but completed this week is invisible — "missed" is creation-based, not completion-based); `skipped` hard-coded 0; persists `fabric_reports/{weekStart}` on every generation (overwrite semantics); **nothing ever reads these docs back**; UI state lost on reload.

**Server (`functions/src/weeklyReport.ts`, Sundays 19:00 Africa/Lagos):**

- Period = `[now−7d, now]` server-UTC; `weekKey` = run date (Sunday), a different key space than the client's weekStart.
- Expenses queried `date >= sevenDaysAgoIso && date <= nowIso` — string range over ISO dates (breaks silently if any `date` deviates from sortable ISO — UH-FB04).
- **Completion rate counts ALL commitments ever** (unscoped `commitments.get()`, `completed` boolean) yet the push says "X% habits complete" — not a weekly figure (FB-05).
- **`formatCurrency` hardcodes ₦** for all users (FB-05).
- Idempotency: skip if `fabric_reports/{weekKey}` exists; report committed **before** send → mid-notification crash = retry skips (notification silently lost); crash before commit = retry re-sends. Asymmetric; no send log.
- Timezone fixed to Lagos for all users (same class as FB-06/C-05).
- Family/shared rows included, indistinguishable from personal.
- Failure model: runs twice → second pass skipped; delayed run → window relative to run time; missing data → "₦0 spent" notification still sent; duplicate imports (FI-06) inflate totals; streak corruption irrelevant here (booleans); user timezone change → no effect; family disconnect mid-week → previously replicated rows remain counted.

**Retention:** both writers accumulate one doc per week forever; deleted only with the account.

## 14. User feedback / dismissal / deletion

| Action | Semantics | Persists? | Cross-device? | Relearning blocked? |
|---|---|---|---|---|
| `dismissPattern` | **soften** — increments `dismissed`, lowers confidence, drops from `confirmedPatterns` below 0.5; stays in `patterns` | yes (debounced 500 ms) | yes | **NO** — future occurrences re-raise confidence |
| `deletePattern` | delete | yes (debounced) | yes | **NO** — next occurrence recreates the pattern with a NEW UUID (no tombstone); `dismissedPatterns` is not consulted |
| `dismissPrediction` | delete-from-list | yes (immediate) | yes | partially — ID-based; regenerated IDs (date/month-keyed) re-appear next period; some apply pattern-dismiss feedback |
| Proactive-question dismiss | hide | **NO — in-memory only** (`markQuestionShown` sets a field never persisted) | no | NO — reappears every session (FB-09) |
| Mood save | data entry | yes | yes | n/a |
| Clear data (Settings / FabricTransparency) | delete patterns/predictions/settings | yes | yes | deterministic seeding re-creates patterns from the same source history on next init |

Tests: **dismiss→refresh:** pattern remains in the list; **dismiss→reinstall:** persisted doc survives; **delete→same pattern relearned:** YES; **disable→re-enable:** state retained (§15); **account switch:** per-UID; **account deletion:** everything removed (§16).

Distinguish: **hide** (proactive question) / **soften** (dismiss) / **delete** (deletePattern, clear-data) / **prevent-future-learning** — **no mechanism exists** other than disabling Fabric entirely.

## 15. Fabric enable/disable semantics

"Fabric disabled" = the **client feature gate** AND the **per-user server setting** are both evaluated, and they are independent:

1. Build-time/rollout flag `anchor_ai_enabled` (`featureFlags.ts`, default ON in all envs, env-var overridable) gates initialization (`useFabricInitialization.ts:29-34`).
2. Per-user `fabric_settings.state.enabled` (Settings toggle, default **false**) gates everything else (`initializeFabricState` reads it; `FabricService` no-ops learning/predictions/reports/queries when disabled).

When disabled (either gate):

- `initializeFabricState` returns empty arrays and resets the engine — **no subscriptions, no learning, no pattern writes, no predictions, no briefing/insight content** (UI shows a disabled screen); mood save is blocked by `useFabric`'s enabled guard.
- **However the scheduled backend ignores the client flag's absence and reads the same setting directly**: `getFabricEnabledUsers`/`weeklyReport` run for users with `enabled===true` only — disabled users get no nudges/reports. **No data is transmitted externally when disabled.**
- **Existing learned data is RETAINED when disabled** — disabling resets in-memory state only; `fabric_behavior`/`fabric_predictions`/conversations/reports stay in Firestore and are reloaded on re-enable.
- Re-enable: `initialize` reloads behavior + activity; if patterns are empty it **re-seeds from history** (patterns derived from the full transaction/commitment history reappear).

**Answer: disabling Fabric stops processing (subscriptions, learning, generation) — it does not merely hide UI. But it does not delete or stop retaining previously learned data, and re-enable resurrects seed patterns from history.**

Note: `dataCollectionEnabled` is written but never independently read — it always mirrors `enabled` (INFO). The `fabric_suggestions` flag has no consumer (FB-14).

## 17. Family / tenant isolation (Fabric-specific)

- All Fabric state lives under `artifacts/anchor-os/users/{uid}/…` — per-UID by construction (patterns, predictions, reports, briefing is computed not stored, mood, nudge log, analytics, conversations).
- No Fabric code reads `family_connections`, invitations, or another user's tree. Family-derived data enters only as rows pre-replicated into the user's own collections (upstream of Fabric).
- `useFabricLiveSync` and `fabricPersistence` never issue collection-group queries.
- Rules (`config/firestore.rules:186-214`): `fabric_settings`, `fabric_behavior`, `fabric_predictions`, `fabric_conversations`, `fabric_reports` = **owner read+write only**; `mood_entries` = owner-only **with field/type validation** (`isValidMoodEntry`, rules:38-45,177-186); `fabric_analytics`, `fabric_nudge_log` = owner read, **write: false** (Admin SDK only).
- **User A substituting User B's UID** in any Fabric read/write fails the `request.auth.uid == userId` predicate on every Fabric path (default-deny elsewhere; no family predicate exists on Fabric collections at all). No collection-group or Admin-SDK Fabric path bypasses this (the only Admin Fabric writes target the caller's own user doc).
- Server functions (`fabricNudges`, `weeklyReport`) read only the user's own subtree with the Admin SDK and write only back into it.

**Verdict: Fabric adds no family/tenant-isolation surface beyond FS-01.** FS-01's post-disconnect read exposure exists in the upstream finance/commitment/dashboard rules; Fabric consumes those rows only from the user's own collections, so Fabric neither widens nor narrows FS-01. No new isolation finding.

## 18. Account deletion / retention (cross-ref A-04)

`deleteMyAccount` (`functions/src/deleteAccount.ts:19-38,123-127`) calls `deleteDocumentTree(users/{uid})` — recursive deletion of **all subcollections**, which includes: `fabric_settings`, `fabric_behavior`, `fabric_predictions`, `fabric_conversations`, `fabric_reports`, `mood_entries`, `fabric_nudge_log`, `fabric_analytics`, `fcmTokens`. Fabric data lives entirely below the user tree → **deleted with the account** (subject to A-04's non-transactionality caveat — a mid-deletion failure can leave a partially erased tree, per A-04).

- No Fabric artifact lives outside `users/{uid}` (no global collections, no external provider records — none exist).
- Scheduled jobs after deletion: `getFabricEnabledUsers`/`weeklyReport` iterate `users` — a deleted user's doc is gone → excluded; no orphaned schedules (schedules are global, iterating per-user state).
- Cloud Functions **platform logs** may retain invocation metadata (not user data payloads; nudge bodies contain titles/amounts only in FCM payloads, not logs — `reminderSender` logs token prefixes only).
- Analytics events (`fabric_analytics`) are under the user tree → deleted. Sentry/telemetry breadcrumbs (client) can contain `userId` in init events; outside this audit's retention scope.

**Verdict: Fabric retention after account deletion = none below Firebase, none external; residual risk is A-04's partial-erasure window, not Fabric-specific.**

## 31. Findings (confirmed defects)

### FB-01 · Singleton `FabricService` can persist User A's patterns into User B's `fabric_behavior` · MEDIUM · PROVEN (code path)
- Paths/symbols: `src/services/fabric/FabricService.ts:43-55 (initialize), 146-150 (dispose), 161-170 (scheduleSave)`; `src/context/fabric/useFabricInitialization.ts:65-70`.
- Flow: A logs out → cleanup runs `dispose()` (cancels timer ONLY; `activeUserId`, `enabled`, and engine state survive) → B logs in → `initialize(B)` sets `activeUserId=B` synchronously, then awaits settings/profile/behavior/activity reads → any `learnFrom` in that window records into A's still-loaded engine state and schedules `saveBehavior(B)` → A's patterns/confidences are **written under B's UID** (rules allow it: B's own tree).
- Expected invariant: service state must be keyed/reset per active user before any write can target a new UID.
- Actual: no reset on user switch; debounce persists stale-state under the new UID.
- Reproducible scenario: shared device; A logs out; B logs in; B immediately adds an expense (FinanceContext learns on mount paths) while B's init awaits Firestore.
- Privacy/user impact: cross-user contamination of learned-state; patterns derived from A's behavior influence B's predictions; persisted (survives sessions).
- Blast radius: per-user document; no cross-user READ exposure.
- Mitigation present: `useFabric` guards learning when `isEnabled` false — but `isEnabled` can already be true mid-init. Test coverage: none for service-level switch.
- Remediation direction: reset service state at initialize start (or key state by UID and verify before save).

### FB-02 · Fabric learns events that never committed (offline queue + optimistic toggles) · MEDIUM · PROVEN (code path)
- Paths: `src/hooks/useFinanceOperations.ts:88-93` (offline `enqueueOffline` → return), `src/context/FinanceContext.tsx:18-28` (learns after await); `src/context/TaskContext.tsx:21-31` (learns after optimistic toggle); carries C-01/C-02/FI-06.
- Expected invariant: learning should key off authoritative commit (transaction/success callback).
- Actual: offline adds resolve without commit and still teach; duplicated queue flushes teach repeatedly; optimistic completions (incl. those rolled back by C-03 races) teach.
- Impact: persistent false patterns biasing predictions/briefing/proactive questions; permanent until manual deletion (§9).
- Remediation direction: emit learning events from the authoritative success path only (transaction completion / queue-flush ack) with an event id for dedupe.

### FB-03 · Deletion/reversal permanently reinforces learned patterns · LOW · PROVEN
- `FinanceContext.deleteTransactionWithLearn` teaches `transaction_recorded→review_budget` for the deleted transaction's category; `BehavioralEngine` has no decrement/compensation; seed patterns built at first init never retract when source transactions are later deleted.
- Impact: reversed/duplicate transactions (FI-06/FI-08) leave permanent pattern bias; `missed_habit` question fires from seeded `lastOccurred` (wrong by construction).
- Remediation direction: compensation events on delete; rebuild/decay patterns when source data changes materially.
