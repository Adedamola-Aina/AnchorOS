# AnchorOS Product Specification

Durable product semantics — what AnchorOS does and the behavior contracts it must honor. Executable truth lives in `src/`, `functions/`, and tests.

> "The application should feel like an anchor. Calm. Stable. Trustworthy. Never flashy. Never manipulative."

## Product soul

- A **personal operating system**: context-aware, permission-aware, behavior-aware.
- Tone: honest, clear, quietly helpful. Prioritize human behavior over technical convenience.
- Every feature **removes a decision the user should not have to make** and reveals only what matters now.

## Dependency fabric ("what before how")

| Dependency | Contract |
|---|---|
| Authentication | Gatekeeper for everything |
| Email verification | Required for explicit trust actions (sending invites, email notifications); UX must explain *why* it is needed when blocking |
| Accounts | The container. Empty state welcomes and offers a single "Create Account" action |
| Transactions | One account for income/expense; **two** accounts for a transfer |
| Trends | Depend on data existence; handle the "new account" state gracefully (hide or explain) |
| Family mode | Verified email → invite → accept → owner shares accounts. **"Accepted" ≠ "Access granted"** — the owner toggles sharing |
| Notifications | Generated by shared-account activity; inline first; email overflow only if preferences enabled + email verified |

## Finance experience

- **Account-first, not transaction-first**: opening an account makes it the active context; creating a transaction never restates the account (implicit source).
- **Account detail** is self-contained: history, trends, recurring payments.
- **Global history** is the single source of truth across accounts, filterable.
- **Transfers** are atomic, creating **two linked transactions** (source debit + destination credit); editing/deleting one updates/removes the other; same source/destination is prevented.
- **Deletion**: accounts soft-delete (archive, warn about orphans/access loss); user deletion is hard and severe.

## Family sharing journey

1. Owner (verified email) sends a unique-token invite.
2. Recipient accepts via link → login/register → users linked.
3. Owner toggles sharing per account in Settings.
4. Invitee sees shared accounts (marked relative to owner).
5. Unsharing revokes access **immediately**; history remains.

## Shared awareness (notifications)

- Trigger: an action by the *other* user on a shared account.
- Human-readable summaries ("Sarah added Groceries - $45.00").
- Slim, actionable, dismissible banners (max 4 inline); **per-user dismissal**.
- Overflow groups bursts ("5 transactions added") into email digests; frequency instant/daily/weekly.

## Analytics & dashboard

- 30-day income vs spending, grouped by week; tap a bar to filter history (charts are navigational tools).
- Dashboard = "How am I doing right now?": net-worth snapshot, 7-day cash flow with momentum, asset distribution, recent activity, productivity score (when commitments exist).

## Error & integrity UX

"Errors are not the user's fault."
- Network → retry; validation → specific, highlighted fix; prerequisite → guide to resolution.
- Multi-record updates (transfers) use database transactions; notification creation is atomic.

## Design imperatives

1. Anticipate intent · 2. Respect privacy boundaries · 3. Surface insight, not data · 4. Stay visually calm · 5. Context-, permission-, behavior-aware by default. See [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) for the visual contract.
